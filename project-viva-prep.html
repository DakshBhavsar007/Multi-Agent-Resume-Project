Authentication & Middleware Architecture

The application implements a multi-role authentication system that supports dual lookup by email or username:

  • Backend Authenticator (api/backends.py): EmailOrUsernameModelBackend allows users to authenticate using either their registered email or username across different account models.
  • Custom Middleware Stack (api/middleware.py):
    • SecurityHeadersMiddleware: Injects defensive headers (HSTS, X-Frame-Options, CSP, X-Content-Type-Options).
    • ExceptionSanitizationMiddleware: Catches raw exceptions in production and strips sensitive tracebacks to prevent information disclosure.
    • UsageLoggerMiddleware: Logs request counts, response latency, and endpoint metrics.

4. Asynchronous Pipeline & Celery Tasks

Background processing is handled by Celery tasks defined in backend/workers/celery_worker.py. This decouples long-running file operations and AI calls from the synchronous HTTP request/response cycle.

Task Name Triggering Mechanism Operation & Retry Strategy Rationale for Async Execution
process_resume_batch POST to /api/v1/sessions/{id}/candidates or batch upload Parses raw PDF/DOCX files via PyMuPDF/pdfplumber, extracts text, invokes LLM parsing fallback, computes match scores. max_retries=2. File parsing and LLM inference take 3–15 seconds per file. Async execution prevents HTTP gateway timeouts.
enrich_candidates_llm Triggered after batch resume ingestion completes Passes parsed candidate text to Google Gemini to extract nuanced qualitative insights, soft skills, and missing qualifications. max_retries=1. LLM rate limits and network latency require non-blocking processing.
match_all_candidates POST to /api/v1/sessions/{id}/match-all Re-computes semantic similarity and weighted criteria scores for all candidates in a recruitment session against updated JD criteria. Re-evaluating hundreds of candidates involves vector matrix computations that block web threads.
sync_gmail_resumes Manual trigger or scheduled recruitment sync Connects via Gmail API, queries attachments matching search criteria, downloads PDFs, and enqueues batch ingestion. External API polling and OAuth token refreshes are prone to network delays.
release_round_results Recruiter completes assessment round evaluation Generates candidate scorecard notifications and dispatches transactional emails via Brevo. Third-party email dispatch should never delay the UI response.

5. Frontend Deep-Dive (Vite + React SPA)

The frontend is organized into modular page routes with dedicated state management stores per user role.

State Management Architecture (Zustand Stores)

  • authStore.js: Stores Recruiter/Company JWT tokens, company profile data, and session status in localStorage.
  • seekerAuthStore.js: Stores Job Seeker JWT tokens and personal application status.
  • portalAuthStore.js: Manages Developer API credentials and developer portal session state.
  • adminAuthStore.js: Manages Superadmin authentication tokens.
  • sessionStore.js & candidateStore.js: Holds active workspace filter state, candidate selections, and sorting parameters.

API Client Layer (frontend/src/lib/api.js)

All network requests pass through a consolidated req() fetch wrapper in api.js:

  • Dynamic Base URL Resolution: Automatically detects whether the app is running on localhost:5173 (routing to http://127.0.0.1:8000/api/v1) or production.
  • Multi-Header Token Injection: Automatically attaches appropriate headers: Authorization: Bearer <jwt>, X-Seeker-Token, X-Developer-Token, or X-API-Key.
  • Automatic Ban & Timeout Handling: Includes a 30-second AbortController timeout and catches 401/403 responses indicating account suspension, triggering auto-clearing of state and redirection to /login.

6. Cross-Cutting Concerns

1. End-to-End Authentication & Authorization Flow

The platform implements stateless JWT authentication across multiple account types:

  1. Client sends credentials to POST /api/v1/auth/login (or /seeker/login).
  2. Backend validates against EmailOrUsernameModelBackend and issues a signed JWT token using JWT_SECRET with an expiration (default 24 hours).
  3. Frontend stores the token in localStorage and updates the corresponding Zustand store.
  4. Subsequent API requests attach the token in HTTP headers. The backend's custom decorators (@jwt_required, @seeker_jwt_required) verify the signature and attach the user object to `request.company` or `request.seeker`.

2. Environmental Configuration Management

The backend loads variables from `.env` using python-dotenv. Critical environment variables (DATABASE_URL, JWT_SECRET, GEMINI_API_KEY) are validated upon Django startup in settings.py. Missing critical keys raise an immediate ValueError to prevent silent startup failures.

7. Known Issues, Technical Trade-Offs & Workarounds

Explicit Disclosure of Workarounds & Stubbed Features: During viva defenses, examiners appreciate honesty regarding real-world compromises. Below are actual technical trade-offs present in the codebase:
  • Python 3.12 Compatibility Polyfill (settings.py): Python 3.12 removed pkg_resources from standard library distributions. To prevent AttributeError crashes from third-party packages like razorpay, a dynamic mock object polyfill was added at the top of settings.py.
  • Render Free Tier Port Scan Workaround (start_celery.py): Render's Web Service hosting requires an active HTTP listener on a designated $PORT, or the deployment fails health checks. Because Celery workers are background consumers without HTTP interfaces, start_celery.py spawns a lightweight background Python http.server thread purely to reply 200 OK to Render's health checker while launching Celery in the main process.
  • Database Protocol String Transformation (settings.py): Async connection strings formatted for SQLAlchemy (postgresql+asyncpg://) in .env are dynamically patched via string replacement to standard postgresql:// so Django's synchronous dj_database_url parser can consume them without failing.
  • Sandbox Integration Status (piston_sandbox.py): Candidate coding round evaluations use Piston API integration wrappers in piston_sandbox.py. If remote execution endpoints are unavailable, fallback mock execution is used.

8. Comprehensive Viva Question Bank (50+ Questions)

Model answers are written in the first person ("I chose...", "We implemented..."), reflecting direct engineering responsibility.

Section A: Architecture & System Design

Q1. Explain the high-level architecture of your application.
I built the application using a decoupled architecture: a React 18 Single Page Application on the frontend and a Django REST backend. For intensive background workloads like resume parsing and LLM scoring, I integrated a Celery task queue backed by Redis. This keeps HTTP request cycle latency minimal while offloading heavy computations.
Q2. Why did you choose Django over FastAPI or Express.js?
I selected Django primarily for its robust, built-in ORM, mature migration system, and out-of-the-box admin panel. Since our application involves complex relational models—such as Companies, Candidates, Sessions, and Assessment Rounds—Django's ORM allowed rapid schema modeling and reliable transactional management.
Q3. TRAP QUESTION Why use Celery with Redis instead of native Django async views?
Django async views handle I/O-bound concurrency well within a single web process, but long-running tasks like multi-page PDF text extraction and LLM API calls can consume worker memory and survive beyond client HTTP connection dropouts. Celery provides distributed task persistence, configurable retry logic, and multi-threaded worker pools isolated from web server resources.
Q4. How does your system handle database switching between Development and Production?
In settings.py, I used dj-database-url to parse the DATABASE_URL environment variable. If a PostgreSQL connection string is provided (e.g. on Render), Django configures PostgreSQL with connection health checks; otherwise, it falls back seamlessly to a local db.sqlite3 file for local development.
Q5. What happens if the Redis broker goes down while a user uploads resumes?
If Redis is unreachable, the synchronous Django view catches the connection error and falls back to running synchronous resume parsing inline, or returns an explicit error message to the frontend asking the user to retry while logging the broker failure.

Section B: Backend & Django ORM

Q6. How did you implement multi-role authentication in Django?
I implemented a custom authentication backend, EmailOrUsernameModelBackend, inside api/backends.py. This allows both recruiters (Company accounts) and job seekers to authenticate using either email or username against their respective database models.
Q7. How do you prevent N+1 query problems in candidate listing endpoints?
I utilized Django's select_related() for foreign key relationships (such as joining Company on Session) and prefetch_related() for many-to-many or reverse relations. For aggregate counts (like applicant totals), I used ORM annotations with Count().
Q8. TRAP QUESTION Why are you storing JSON data in notification_settings instead of a separate table?
The notification preferences represent key-value user settings that do not require relational joins or indexing. Using Django's JSONField avoids unnecessary table join overhead for simple configuration dictionary lookups.
Q9. Explain the role of custom middlewares in your backend.
I authored three key middlewares in api/middleware.py: SecurityHeadersMiddleware for enforcing HTTP security policies, ExceptionSanitizationMiddleware for shielding raw database tracebacks in production, and UsageLoggerMiddleware to track request response metrics.
Q10. How do you handle password security?
Passwords are hashed using PBKDF2 with SHA-256 (Django's default password hashers) before storage. Raw passwords are never stored or logged in plain text.

Section C: Asynchronous Workers & AI Pipeline

Q11. Describe the step-by-step pipeline when a recruiter uploads 50 resumes.
When uploaded, files are saved locally to `UPLOAD_DIR`, an IngestJob record is created, and process_resume_batch.delay() is dispatched to Celery. The worker extracts text using PyMuPDF, normalizes skills against SkillTaxonomy, evaluates candidate match scores against job description criteria, and updates candidate database records asynchronously.
Q12. What is your LLM fallback strategy if Google Gemini API hits a rate limit?
I designed a multi-tier fallback mechanism: if Google Gemini fails due to rate limits or network issues, the system catches the exception and falls back to Groq Cloud API (Llama 3.3), and finally to a locally hosted Ollama instance if available.
Q13. TRAP QUESTION Why run Celery workers with --pool=threads on Windows in run.bat?
Celery's default prefork pool uses Unix-specific fork() system calls, which fail under Windows environments. Using --pool=threads (or --pool=solo) ensures thread-safe worker execution without process-spawning crashes during local Windows development.
Q14. How do candidate assessment results get communicated to applicants?
When a recruiter triggers result release, the release_round_results Celery task queries candidate attempts, formats personalized status scorecards, and sends transactional emails via the Brevo API through django-anymail.
Q15. What library do you use for PDF parsing and why?
I primarily use PyMuPDF (fitz) with pdfplumber as a fallback. PyMuPDF is significantly faster than PyPDF2 and accurately extracts text layouts and multi-column tables common in modern resume designs.

Section D: Frontend Architecture

Q16. Why use both Zustand and TanStack React Query in the frontend?
I separated client-side state from server-side state. Zustand manages persistent local UI state (such as active user sessions and modal visibility), while TanStack React Query manages API data fetching, automatic background refetching, and caching with a 5-minute stale-time.
Q17. How does your frontend API client handle token expiration?
In frontend/src/lib/api.js, the centralized req() fetch wrapper checks for 401 Unauthorized responses. If detected, it automatically clears localStorage, resets Zustand auth state, and redirects the user to /login.
Q18. TRAP QUESTION Why configure custom Rollup manual chunks in vite.config.js?
Our application uses large libraries like Framer Motion, GSAP, Recharts, and Lucide React. Without custom chunking, Vite produces a single giant JavaScript bundle. By splitting vendor dependencies into separate chunks, browser caching efficiency is improved and initial page load times decrease significantly.
Q19. How is route protection implemented in React Router?
I wrapped protected routes in a ProtectedRoute component that reads auth state from the Zustand store. Unauthenticated visitors trying to access /dashboard/* routes are automatically redirected to /login.
Q20. What purpose does ScrollToTop serve in App.jsx?
Single Page Applications retain scroll positions across route transitions. ScrollToTop resets scroll position to the top of the viewport on route changes using requestAnimationFrame to account for dynamic layout rendering.

Section E: Deployment & Operations

Q21. Explain the deployment setup for backend and workers.
The Django web backend is deployed as a Web Service on Render running Gunicorn. Celery workers run as a separate service instance connected to a managed Redis instance. The frontend SPA is built via Vite and deployed on Vercel.
Q22. Why does start_celery.py run a background HTTP server?
Render's free tier Web Service checks require an open HTTP port. Because Celery workers do not listen on HTTP ports, I added a lightweight HTTP server thread inside start_celery.py that listens on $PORT and responds 200 OK to pass health checks.
Q23. How are CORS policy headers configured?
CORS is managed using django-cors-headers. In settings.py, allowed origins are parsed from the ALLOWED_ORIGINS environment variable, restricting API access to trusted frontend domains like https://between.indevs.in and local development origins.
Q24. How would you scale this system to handle 10,000 daily resume uploads?
To scale, I would move resume uploads to AWS S3 / Cloudflare R2 object storage instead of local disk storage, scale Celery worker nodes horizontally behind Redis, and introduce PostgreSQL read-replicas for candidate query heavy endpoints.
Q25. How are API keys secured for public developer APIs?
Developer API keys consist of a public identifier and a secret key generated via UUID and cryptographic hashing. The secret key is shown once during generation, and incoming API calls are validated using the X-API-Key header against hashed database records.
